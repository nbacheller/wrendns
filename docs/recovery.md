# Recovering from a guarded change

Some settings can lock every admin out, put passwords on the wire, re-encrypt your stored secrets, or replace a node's configuration. TelltaleDNS calls them **guarded** and changes them with a review, a phrase you type, an audit record and (for addresses) a window that rolls the change back by itself ([Guarded changes](running.md#guarded-changes)). This page is the way back when one of them goes wrong anyway. None of it needs the web UI.

**The rule that makes recovery possible:** a value set in a configuration file always wins over one set in the UI. Setting the field in the file and restarting the node is always the first fix.

## The three ways back

1. **Edit the file and restart.** Put the setting (for example `[api] listen = "127.0.0.1:8053"`) in the node's configuration file and restart it. A file's value wins over the stored one, and the UI then shows the control as "set by file".
2. **Clear the stored entries, offline.** With the node stopped, `telltale guarded list -c /etc/telltale/telltale.toml` prints each stored guarded entry (staged, on probation, active, hidden by a local clear), and `telltale guarded clear <id>` (or `--all`) removes them. It needs the node stopped (it opens `state.db`; it refuses while a node holds the data directory), is audited as `cli:<os user>`, clears only that node's entries and says what the node will use afterwards. On a cluster replica the primary still holds its copy and replicates it back, so the clear is also recorded locally: the node ignores that entry's replicated value until the primary's copy changes.
3. **Start once with `TELLTALE_IGNORE_GUARDED=1`.** The node ignores every stored guarded entry (nothing is deleted) and runs on its files alone, logs it at warning level, and shows the health reason `guarded_ignored` until you remove the variable. It never ignores the file. In Kubernetes set the variable on the pod and let it restart; there is no need to run the command in the container.

Two failed starts also fix a *staged* change on their own: a node that starts with a staged or restored entry marks it on **probation**, writes a counter to `<data_dir>/guarded-probation`, and if it is not healthy (state opened, API listener bound, its own DNS answering, and for the secrets key an unlocked store) within `max(confirm_window_secs, 180)` seconds, twice in a row, it drops the entry (audited `settings.guarded_rolled_back`, reason `failed_start`) and starts from the file. A power cut counts as a failed start.

## Symptoms and fixes

| Symptom | Cause | Fix |
|---|---|---|
| The UI is unreachable after changing the API address (`api-address`) or its certificate (`api-tls`) | The change was kept (you confirmed it through the new address) and the address or certificate turned out wrong later | Set `[api] listen` / `[api] tls` in the file and restart, or `telltale guarded clear api-address` (or `api-tls`) with the node stopped. Systemd: `systemctl stop telltale`, clear, `systemctl start telltale`. Compose: `docker compose stop`, run the command in a one-off container on the same volume, `docker compose start`. Kubernetes: set `TELLTALE_IGNORE_GUARDED=1` on the pod. |
| No DNS after changing a listener (`listen`) | The new listener address is wrong, or a port the host doesn't publish (Docker and Kubernetes don't change published ports) | The window rolls back an unconfirmed `listen` change by itself. For a confirmed one: set `[[listen]]` in the file and restart, or clear `listen`. A listener that can't bind at start falls back to the file for that start (health reason `guarded_bind_fallback`) and is tried again next start. |
| Can't sign in behind a proxy; every client looks like the proxy (`trusted-proxies`) | The list names the wrong proxy, so `X-Forwarded-For` is ignored (or the right one is missing), or break-glass networks no longer match | Set `[api] trusted_proxies` in the file and restart, or clear `trusted-proxies`. A pending proxy list is used only to evaluate the confirm step until you confirm it. |
| The secret store is locked after changing the key (`secrets-key`) | The new key file can't be read, or it is not the key the rows are under | Two failed starts drop the staged key and the node starts from the file; if some rows were already re-encrypted the fallback keeps both key paths (the new key as `secrets_previous_key_file`) and reports `secrets_rotation_incomplete`. Fix by hand: `telltale secrets rotate-key` and [docs/secrets.md](secrets.md). |
| A secret reference is refused after widening or narrowing `secret-file-dirs`; credentials are sent in clear after `allow-secrets-over-http` or `allow-insecure-basic` | The setting was changed | They are `immediate` changes with no window: set the field back in the form, in the file, or clear the entry. The audit record `settings.guarded` holds the previous value. |
| The watchdog is off and a hang went unnoticed (`watchdog`); a configuration file path is wrong (`file-paths`) | Turning the watchdog off hides a hang; a path lets the server read a file you name (the T23.2 rules still apply) | Set `[watchdog]` or the path in the file, or clear the entry. |
| A node will not join, or joined the wrong cluster (`cluster-init`, `cluster-join`, `cluster-leave`, `cluster-git`) | A cluster action was made with the wrong values | `telltale cluster` offline commands and [docs/running.md](running.md#clustering); an action is one operation with its own preview and audit, not a stored value, so there is nothing to clear except a `cluster-git` source (`telltale guarded clear cluster-git`). |
| No admin accounts after a data directory move (`data-dir`) | The new directory has no `state.db`, so first-run setup reopened | The move only applies at a restart and was previewed with this warning. Set `[node] data_dir` back in the file, or `telltale guarded clear data-dir` (it reads the pointer from the directory the file names). Nothing moves `cluster/`, so the node's cluster identity never leaves the old directory. |
| The node's name changed and it lost its place (`node-identity`) | The staged identity applied at the next start | Two failed starts drop it; or set `[node] name` in the file, or clear `node-identity`. |
| **"Restart now" did not bring the node back** (`restart-now`) | The node exited with status 75 and nothing started it again: the unit has `Restart=no`, the pod has no owner, or `TELLTALE_SUPERVISOR` was set by hand on an unsupervised run | Start it yourself. The shipped systemd unit, Compose bundles and Helm chart restart the node and declare `TELLTALE_SUPERVISOR`; a bare `docker run`, a hand-made unit or a pod without a controller has no supervisor, and the button is not offered there. If the node starts and stops again, use one of the three ways above. |

## What the node records

Every guarded change writes `settings.guarded` (the setting, node, mode, before and after with credentials redacted, the reason, who, the source address), a rollback writes `settings.guarded_rolled_back` (reason `expired`, `cancelled`, `commit_failed`, `bind_failed` or `failed_start`), a refused attempt writes `settings.guarded_refused` (no values in it), an accepted restart writes `settings.guarded_restart`, and an offline clear writes `settings.guarded_cleared`. The `guarded_setting_changed` alert condition goes out when a change is applied or staged and again on its outcome, so a second channel sees a change made with a stolen admin session.
