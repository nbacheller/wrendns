# 01 — Requirements (the contract)

Every requirement has a stable ID. Code, tests, and PRs **must** reference IDs (e.g., `// REQ: FLT-004`, test name `flt_004_wildcard_suffix_block`). Priority: **P0** = v1.0 must ship; **P1** = v1.x; **P2** = later / stretch.

Detailed behavior lives in the referenced spec section. If this table and a section disagree, the section wins, and fix the table.

## DNS core (DNS) — see `03`
| ID | Pri | Requirement |
|---|---|---|
| DNS-001 | P0 | Serve DNS over UDP and TCP (RFC 1035, RFC 7766) on configurable addresses/ports, IPv4 and IPv6. |
| DNS-002 | P0 | Serve DoT (RFC 7858) with configurable cert/key, plus ACME (via cert files that cert-manager mounts in k8s). |
| DNS-003 | P0 | Serve DoH (RFC 8484) over HTTP/2 with GET and POST on `/dns-query` and `/dns-query/{client-id}`. |
| DNS-004 | P1 | Serve DoH over HTTP/3 and DoQ (RFC 9250). |
| DNS-005 | P0 | EDNS(0) (RFC 6891), with a configurable advertised UDP payload size (default 1232) and TC-bit truncation. |
| DNS-006 | P0 | Sharded in-memory cache that stores wire-format responses and rewrites ID and TTLs on hit; honors min/max TTL clamps; negative caching (RFC 2308). |
| DNS-007 | P0 | Serve-stale (RFC 8767), with configurable max stale age and client-response timeout. |
| DNS-008 | P1 | Prefetch: hot entries refresh asynchronously when remaining TTL < 10% (configurable). |
| DNS-009 | P1 | Cache persistence: an optional dump on shutdown and load on startup. |
| DNS-010 | P0 | Local records: A, AAAA, CNAME, PTR (auto-generated from A/AAAA), TXT, SRV, MX; wildcard local records; hosts-file import. |
| DNS-011 | P0 | DNSSEC validation (RFC 4033–4035) for forwarded and recursive answers. Bogus → SERVFAIL with EDE 6. Configurable negative trust anchors. |
| DNS-012 | P1 | Full recursive resolution from root hints, with QNAME minimization (RFC 9156) and aggressive NSEC caching (RFC 8198). |
| DNS-013 | P0 | Extended DNS Errors (RFC 8914) on blocked, stale, and failed answers. |
| DNS-014 | P0 | Per-client rate limiting (token bucket; default 1000 q/60 s like Pi-hole), with REFUSED or drop as the action and an allowlist exemption. |
| DNS-015 | P1 | ECS (RFC 7871): strip, pass through, or substitute per upstream; never leak ECS by default. |
| DNS-016 | P1 | DNS64 (RFC 6147) per group. |
| DNS-017 | P0 | Conditional forwarding / per-domain upstream routing, including reverse zones (Pi-hole `rev-server` parity). |
| DNS-018 | P1 | Local zones: a small authoritative zone loaded from an RFC 1035 zone file or config (split-horizon views per group). |
| DNS-019 | P0 | Refuse ANY queries (RFC 8482 minimal response), refuse zone transfers (AXFR, IXFR) without forwarding, and drop malformed packets cheaply. **Special names** (`spec/03` §3 step 4; ADR-014, ADR-904), answered without forwarding: `localhost`, `*.invalid`, the Firefox canary, CHAOS class, private reverse zones, iCloud Private Relay's `mask.icloud.com`/`mask-h2.icloud.com` (NXDOMAIN, on by default), `resolver.arpa` (never forwarded; DDR, RFC 9462, for this node's reachable encrypted listeners when `[special] ddr_name` is set, else no data), and optionally (`single_label_nxdomain`, off by default; Pi-hole's `domain-needed`) NXDOMAIN for single-label A/AAAA/HTTPS names that no local data, zone, device name or route covers. The Pi-hole importer maps the matching settings. |
| DNS-020 | P1 | PROXY protocol v2 on TCP/DoT/DoH listeners, to preserve client IPs behind load balancers. |
| DNS-021 | P2 | NSID (RFC 5001), off by default: a query that asks for it gets the answering node's name, so a client can tell which node or pod answered behind a shared address (owner request 2026-10-09, from Technitium #1932). |
| DNS-022 | P1 | **Stub zones** (BIND `static-stub`, Unbound `stub-zone`): a domain whose own servers are authoritative only is resolved iteratively starting at those servers instead of the root, following the delegations they give, with a health check they answer (the zone's SOA); set from the config, the API (`stub: true` on a forward), MCP, and the UI (community request 2026-11-14, PR #10). |
| DNS-023 | P1 | **Device names in DNS** (fork owner request 2026-11-16; community request: DNS kept in step with DHCP leases and static leases, without a DHCP server, ADR-091): with `[local] device_domain` (off by default), every device WrenDNS knows by name answers an A record `<name>.<domain>` and a PTR for its address: named devices with one address or a MAC, the routers' DHCP clients and reservations and Home Assistant's devices (`[[router]]`), the other nodes' routers (CLU-002), and with `device_mdns` the names devices announce. Names become one DNS label (`Kitchen Tablet` → `kitchen-tablet`); when two devices want one label, one keeps it by a fixed order (ADR-901). Configured records, hosts files, and a zone's own records win; a device name inside a zone answers before the zone's NXDOMAIN. Built off the query path; the query path pays one branch with it off and one lock-free load with it on (`02` §3). `GET /api/v1/dhcp/leases` shows each device's `dnsName`; explain says when a device name answered. A device the routers report with IPv6 addresses also answers AAAA for each usable one and has an `ip6.arpa` PTR, by the same label and offline rules (T24.8, ADR-983). Discovery data never names a device in DNS (ADR-910). That covers SNMP, imports, the neighbour-table inventory source, UniFi `stat/alluser`/`stat/device` and Home Assistant devices without entities. With `device_inventory_addresses` on, discovery may only supply the address of a device that is already named (DSC-012). |
| DNS-901 | P1 | **A public listener is never an open resolver** (T36.2, ADR-1050 point 5, ADR-1090; spec/08 §6). A `dot`, `doh`, `doh3` or `doq` listener with the gate on answers only a query that carries a known device key: the DoH or DoH3 path `/dns-query/<key>` or the first label of the DoT or DoQ server name; a key in a server name is sent in clear and gets public answers only (ADR-1050 point 5). A key is at least 128 random bits (26 or more base32 characters, `a-z` and `2-7`) and the `id:` match key of a configured device; a short or readable ID is never a key here. A missing, an unknown and a revoked key are refused identically within a transport (DoH 404 as ADR-039, before the body is read; DoT and DoQ REFUSED with extended error 18) and counted (`wrendns_client_id_refused_total{transport}`), and refusals are rate limited per address (an IPv6 /64 is one) and per key (`wrendns_client_id_limited_total`). A known key is answered from any address, outside `[access] allowed_networks` too; every other stream keeps `allowed_networks`. A refused query never reaches a cache, a list or an upstream. The check is two hash lookups and costs no allocation for a known key. **On by default for a listener bound to a public address** (not loopback, RFC 1918, CGNAT 100.64/10, link-local or ULA; ADR-1090 point 1, owner decision 2026-11-25), off by default otherwise: `require_client_id` is unset, `true` or `false`; a wildcard bind (`0.0.0.0`, `[::]`, `[::ffff:0.0.0.0]`) is on by default only when the host holds a public IPv4 address (a global IPv6 address alone does not gate it and the node warns; an unreadable interface list gates it; the host's addresses are read at start and at every reload, and the health reason `listener_gate_stale` shows a change since bind; ADR-1090 point 9); an explicit `false` on a public or public-resolving listener is allowed with a warning at start and at every reload (file or UI) and a UI warning; `udp` and `tcp` are never gated. An upgrade that turns the gate on is visible: a startup log line naming the listener, the health reason `listener_gate_default`, the UI notice and the refusal metric. Settings → System → Listener access shows each listener's gate with a warning for a public address without it, and the help topic `listener-keys` explains it; the flag is set in the config file until the guarded `listen` row (T27.14) lets the UI edit listeners. |

## Filtering (FLT) — see `05`
| ID | Pri | Requirement |
|---|---|---|
| FLT-001 | P0 | List formats: hosts files, plain domain lists, wildcard (`*.example.com`), AdBlock/AdGuard DNS syntax (`||domain^`, `@@`, `$important`, `$badfilter`, `$client`, `$dnstype`, `$denyallow`), Pi-hole regex (with `;querytype=`, `;invert`). |
| FLT-002 | P0 | Domain rules match the domain and all subdomains by default (Technitium semantics), with an exact-match opt-in (Pi-hole "exact" parity). |
| FLT-003 | P0 | Compiled filter snapshot: an FST for domain sets plus a compiled multi-pattern DFA for regexes. Lookup cost is independent of the number of rules. |
| FLT-004 | P0 | Background list download (ETag/If-Modified-Since), compile, and atomic swap with no query pause; the last-good snapshot is kept on failure. Also on demand: `POST /api/v1/lists/refresh`, the Lists page **Update now**, `wrendns ctl lists refresh`, MCP `refresh_lists`, or `SIGUSR1`; in a cluster the primary downloads (ADR-905). |
| FLT-005 | P0 | Groups (Pi-hole model): clients → groups → {lists, allow/deny rules, upstream group, schedules, response policy}. A default group exists. |
| FLT-006 | P0 | Client identification by IP/CIDR, MAC (ARP/NDP neighbor table), hostname (DHCP lease / reverse lookup), client ID (DoH path, DoT/DoQ SNI prefix), and EDNS MAC option (dnsmasq `add-mac` format). |
| FLT-007 | P0 | CNAME deep inspection: block if any CNAME target in the answer chain is blocked for that client. |
| FLT-008 | P0 | Block response modes: NXDOMAIN, NODATA, null IP (0.0.0.0/::), custom IPs, REFUSED; always with EDE 15 (Blocked) or 17 (Filtered) plus the rule attribution text (configurable). |
| FLT-009 | P0 | Global and per-group pause (disable blocking for N minutes), with auto-resume. |
| FLT-010 | P1 | Schedules: per-group weekly time windows that enable extra lists or block all ("bedtime"). |
| FLT-011 | P1 | Safe-search enforcement (Google, Bing, DuckDuckGo, YouTube restricted, Pixabay…) via CNAME/A rewrites per group. |
| FLT-012 | P1 | Blocked-services presets (one-click service bundles: TikTok, Facebook, gaming, etc.), shipped as data files. |
| FLT-013 | P0 | Rule attribution: every block or allow decision records list ID + rule ID, and the API can explain "why was X blocked for client Y". |
| FLT-014 | P1 | Rewrites (`$dnsrewrite`-like): map a domain to an answer per group. |
| FLT-015 | P1 | Response IP filtering: block answers whose A/AAAA falls in a configured CIDR (DNS rebinding protection; private IPs from public names). |
| FLT-016 | P2 | Per-group AAAA filtering: a group's AAAA questions get no data (devices fall back to IPv4 on a network with broken IPv6); local data still answers, blocks still win, not combined with DNS64 (owner request 2026-10-09, from Pi-hole's feature requests). |
| FLT-017 | P1 | Kubernetes workloads as devices (owner request 2026-10-18): the controller watches the Kubernetes API (pods and namespaces, read-only) and maps each pod address to its workload (`ns/kind/name`, from `ownerReferences`); every device view names the workload, a Deployment's replicas are one device across rollouts (a synthetic analytics key in `100::/64`, RFC 6666), and a workload's group comes from a pod label, a namespace label, a `[[kubernetes.map]]` rule, or `default_group`. One gated lookup on the query path; the API server being down never affects answering (`05` §4, `08` §3.5, ADR-150). |
| FLT-901 | P1 | **Content categories** (owner request 2026-11-18; ADR-994, ADR-995): a catalog (`presets/categories/*.toml`) of categories grouped like UniFi's content filter, each backed by maintained open lists (licence, URL, cadence recorded), downloaded at runtime and shared across groups; a group turns categories on; categories with no open maintained source are listed as not offered. Cost (entries, estimated memory) shown before selecting. |
| FLT-902 | P1 | **Filter profiles** (owner request 2026-11-18; ADR-994): a profile is a group. The Groups page is a profile list (Name, Source, Filter Scope, Safe Search, Schedule) and editor (sources: networks and devices with a private-MAC warning, Ad Block, safe search per engine, Filtering Off, Basic or Enhanced, category picker with search, Select All and Deselect All); devices can be added from the editor. |

A location is a `[[location]]` table with a slug, a label, the networks or VLANs (CIDRs) that belong to it, the serving nodes, an optional parent domain and a visibility of `shared` or `private`. Each table is validated when loaded and on every API write, and a refused table names the bad field and leaves the last good configuration in force. Locations replicate with the cluster configuration. A node that predates the table reads it as absent and does not refuse the configuration. With no `[[location]]` table, names and answers are exactly as before. |
| DSC-909 | P1 | **Location device names** (owner answer 2026-11-20; ADR-1081). A device's name is `<device>.<location>.<domain>`, where `<domain>` is the location's parent domain or, when it has none, the global `[local] device_domain`. The device's location comes from the network it is on (DSC-902 network CIs and router reads). A device on no location's network keeps `<device>.<device_domain>`. The PTR record for each address matches the forward name. Two devices that compose the same name are reported in the CMDB and on the Locations page, and neither name is answered until one is renamed or moved. |
| DSC-910 | P1 | **A moved device keeps its identity** (ADR-1081; DSC-902, DSC-903). A device that moves to another location's network keeps its one CMDB configuration item, and its name changes to the new location's without a new CI. A manual location override set on the device's CMDB record, with a reason, wins over the network until it is cleared. |
| DSC-911 | P1 | **Private location names** (owner answer 2026-11-20; ADR-1081). A name under a `private` location is answered only to a client whose source address is in one of that location's networks. A name under a `shared` location is answered to any client that `[access]` allows. A client on no location's network gets the same answer as for an unknown name, and the reverse (PTR) answer follows the same rule. The source address is the only test: a private name is a split-horizon convenience, not an access control. |
| DSC-912 | P1 | **Location answers on the query path** (ADR-1081; ADR-1031). The client-network-to-location map and the private-name rule are compiled into the policy snapshot when it is built. The query path does no allocation, locking or I/O for them, and `make bench-smoke` is within budget for `wrendns-policy` and `wrendns-cache`, the answer being keyed by the client's location. `explain` and trace output name the location whose name was answered, and the settings-kind entry for `device_domain` is updated in the same change. |
| DSC-913 | P1 | **Locations API, MCP and audit** (ADR-1081; AGT-001..005). `/api/v1/locations` supports create, read, update and remove, with dry run, `Idempotency-Key` and a reason; each device's location can be read through the API. MCP read tools, and one guarded MCP write tool, exist for locations. Every write is audited, and the OpenAPI document is regenerated. |
| DSC-914 | P1 | **Locations page, badges and help** (ADR-1081; the UI-for-every-feature rule). A Locations page lists and edits locations, their networks and serving nodes, and shows the device names that each location composes. A location badge and a location filter appear on the clients list, the network inventory and the CMDB, and the CMDB groups by location. A help topic and Playwright tests named by requirement ship in the same change. |
| DSC-915 | P1 | **Dynamic DNS from the router's WAN address** (owner answer 2026-11-20; ADR-1083). A location's public name follows the WAN address that the router or gateway read already stores in the CMDB. No external address lookup is made. One address change causes one record update, after a debounce, and updates are rate limited (by default one a minute, TTL 60 s). A router WAN address in 100.64.0.0/10 or in a private range is not published, and the panel says why. With no router or gateway read, nothing is published. The record is written through the DNS-provider table (CLD-904), audited, and never written by an agent. A failure is a health reason only, and DNS answers are unaffected (CLU-004). |

## Cloud and provider integrations (CLD) — see `docs/design/hosted.md`
Node-side rows for certificates and DNS providers (#110, ADR-1051 point 7, ADR-1052 point 1), and the node's tunnel client (CLD-901, `spec/14`). The other rows for the hosted service are not in this section yet; spec/10 (M36) names them.

| ID | Pri | Requirement |
|---|---|---|
| CLD-901 | P1 | **The cloud tunnel client** (T36.4; ADR-1047, ADR-1048, ADR-1098, owner decision 2026-11-26; `spec/14`). Every full member of a linked cluster, and never a resolver pod or witness, dials one tunnel to `tunnel.<suffix>:443`: TLS 1.3 only with its own cloud client certificate, the tunnel CA pinned by its key with a backup key and a signed rollover announced at least 30 days ahead, ALPN `wrendns-tunnel/1`, and the node as the HTTP/2 server of the connection it dialled. Each relayed stream starts with a PROXY v2 header whose TLVs carry the server name (checked against the caller's ClientHello), the relay correlation ID and the broker's marks; it is injected in-process into the node's TLS acceptors with a relayed flag, never as a socket; it is always remote, never break-glass, and never matches an IP or MAC client rule, a display's network binding or `allowed_networks`. A header whose address is private, loopback, link-local, RFC 6598, special-purpose (IANA registries, embedded IPv4 forms unwrapped) or in the tenant's LAN ranges (the node's interface prefixes plus `[cloud] lan_networks`) is refused and counted, as is a `LOCAL` command. Separate budgets of 128 DNS and 32 UI streams, classified by the node from the server name, refused past the budget with a counted reason and never queued; large objects travel on blob streams. Control frames are length-prefixed prost frames of the tunnel's own type, at most 1 MiB. Heartbeats every 20 s, each acknowledged; the primary's carries a signed lease. Reconnect with full-jitter backoff from 1 s to 5 minutes. Losing the cloud never changes a DNS answer or the p99 (CLU-004): it is `cloud_unreachable` after 60 s, degraded and never severe. Ships with the `[cloud]` settings, the Settings → WrenDNS Cloud panel, a help topic, the `wrendns_cloud_tunnel_*` metrics and the MCP read tool `cloud_status`. Test: a fake broker in the test tree runs `spec/14` §14's vectors and behaviour tests. |
| CLD-903 | P1 | **Certificates for a cluster's own names** (owner answer 2026-11-20; ADR-1082; T36.10d, T36.7). One issuer node completes ACME DNS-01 for the shared names (the cluster's names, and a location's `*.<location>.<domain>` wildcard when that location opts in) through the provider table (CLD-904). The shared certificates, their chain and the ACME account key are stored secrets, replicated to full members as ADR-917 sets, and each full member installs them with hot reload and no restart. Each node's own name is issued by that node with its own key and is never replicated. Let's Encrypt staging is the default for the first run. Renewal is timed by ARI, raises a health warning 30 days before expiry and a severe reason 7 days before. A failed renewal never affects query answering (CLU-004). Test: a fake ACME server and a mock provider issue and renew a wildcard, and the listener reloads with no dropped query. |
| CLD-904 | P1 | **DNS-provider table** (ADR-1051 point 7, ADR-1052 point 1; T36.10b). A `[[dns_provider]]` table in the node, with Azure DNS, Cloudflare, Route 53 and GoDaddy first, and CNAME delegation of `_acme-challenge` for any other provider. Each credential is a stored secret (ADR-903, ADR-917), referred to by name, scoped as narrowly as the provider allows, and never printed. A test-and-show-scope action reports what the credential can change without showing the secret. Every write is audited. The table is admin-only, no agent token can write through it, and support bundles redact its secrets (API-014). A provider failure is a health reason only. Each first provider passes record create, update and delete against a recorded or mocked API in CI. |
