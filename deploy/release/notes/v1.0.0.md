WrenDNS is a small, fast DNS resolver and ad blocker for a home or small network: it filters each lookup by your rules per device and tells you who asked, what they asked and why it answered the way it did. It runs as one static binary or one signed image on a Raspberry Pi, a Linux host or Kubernetes, alone or as a cluster. This is the first public release, and the first under the WrenDNS name; it began as TelltaleDNS.

## Highlights

- **Every answer has a Why?** Each query is tied to a named device and explained: the list and the line that blocked it, the rule or group that applied, or the upstream that answered, with the time spent in each stage.
- **DNS never depends on anything else.** A node keeps answering from its last good configuration whatever happens to the API, the storage, the telemetry or the rest of the cluster.
- **Filtering your way.** Block and allow lists in hosts, domain and AdGuard syntax compile into one compact index that swaps in atomically. Groups per device, network or VLAN, schedules, safe search, blocked services, rewrites, quick rules, DNS64 and rebinding protection. Content categories and filter profiles (adult, gambling, malware, social, newly registered domains and more) come with Basic and Enhanced presets and a memory budget.
- **Try a change first.** See what a change would have done to yesterday's real traffic before you save it, and run a list in shadow mode, where it counts but never blocks.
- **Encrypted DNS both ways.** Your devices can use DNS over TLS, HTTPS (HTTP/2 and HTTP/3) and QUIC. Upstreams can be DoT, DoH, DoH3, DoQ or DNSCrypt. DNSSEC validation and full recursion from the root are there when you want them.
- **A query log you can search.** 30 days in seconds on a Pi, a "not" on every filter, a live tail, and privacy levels from everything down to counters only.
- **See the network.** A calm dashboard for the whole cluster, one node or one site; a live network map and an optional world view of where lookups go; heatmaps, flows, service-level objectives and error budgets, and a wall display. Device anomalies raise alerts by email, ntfy, Gotify, Pushover, Slack-compatible channels or any webhook.
- **Devices with names.** Names come from your router's leases (UniFi, OPNsense), Home Assistant, mDNS or you, and are answered in DNS under a device domain, with reverse lookups and IPv6. Devices are recognised by type from their maker, their name and the domains they use.
- **An inventory and a CMDB (a configuration database of your devices).** Read-only SNMP v2c and v3 (SHA with AES) reads of your gateway's and switches' ARP, forwarding and LLDP tables, in sandboxed workers; WrenDNS never scans the network itself (`docs/snmp-setup.md`). The CMDB keeps one item for each real thing on the network, with each source's record side by side, and Move, Unlink, Merge and Split to fix a wrong link, each previewed first.
- **A replacement for a Pi-hole pair.** Import from Pi-hole (Teleporter or `gravity.db`, with `dnsmasq.d` lines) or Technitium with a preview of every entry, a Pi-hole compatible API (off by default), several networks served from one node, and failover of a VIP (a shared address that moves between nodes) with keepalived (`deploy/keepalived/`).
- **One cluster, one management plane.** A Pi and Kubernetes nodes share one signed, versioned configuration, and a change made on a replica (any node but the one in charge) goes to the primary. Automatic failover with a witness (a small node that only votes) or a third node, replicated secrets, staged rollouts with automatic rollback, maintenance mode without dropped queries, scheduled failover drills, version pinning, and GitOps from a Git repository.
- **Integrations.** UniFi (names, MACs, networks, VLANs, reservations and offline clients, read-only), Home Assistant names, Kubernetes workloads shown as devices, and a Home Assistant integration with sensors, blocking switches, anomaly events and device quarantine.
- **Ready for scripts and agents.** A documented REST API (`docs/api/openapi.json`), `wrendns ctl` for the shell, and an MCP server on every node, with scoped, rate-limited tokens, a stated reason for every change, dry runs, and plans a person approves. Sign-in is local users and OIDC (Keycloak, Authentik, Entra ID and others) with role mapping, two-factor sign-in and a hash-chained audit log.
- **Signed, light and fast.** Binaries and `SHA256SUMS` are signed with minisign and images with cosign; each binary has an SBOM (a list of what it is built from), and a nightly job checks that two clean builds are the same. `wrendns self-update` checks the signature and the SHA-256 before it swaps and keeps the old binary as `wrendns.old`. The compressed image is held under 25 MiB per architecture by CI, and memory under 32 MiB idle and 128 MiB with 1M blocked names by the release gate. Measured for the release gate (`docs/v1-gate.md`): 170.6k cache-hit queries a second on a development host with two physical cores; 99.999 % of cached and blocked answers within 250 µs in the server, on a 4-CPU node with 1M blocked names; and 52 ms from a cold start to answering.

## Upgrading

**From TelltaleDNS 0.7.x, or an edge build from before the rename:** the name, the command, the paths, the service, the image, the chart and the environment variables have changed. Read "Upgrading to WrenDNS" in `docs/running.md` before you start: it has the steps for a native install, Docker Compose and Helm, and a rollback recipe. An edge build `0.8.0-edge.N` under the WrenDNS name moves to 1.0.0 with `sudo wrendns self-update --restart` (stable is the default channel) or `install.sh`. Its update notice follows the edge channel until then.

### The rename

- **The old names keep working in this release,** each with a warning that says what to use. They are removed in the release after it (decision record ADR-1028 in `spec/11-decisions.md`).

  | Before | Now | In this release |
  |---|---|---|
  | `telltale` (the command) | `wrendns` | `telltale` is a link to `wrendns` and prints a deprecation warning |
  | `/etc/telltale/telltale.toml` | `/etc/wrendns/wrendns.toml` | read when the new file doesn't exist, with a warning |
  | `/var/lib/telltale` | `/var/lib/wrendns` | used when the data directory is the default, the new one doesn't exist and the old one does |
  | `telltale.service`, user `telltale` | `wrendns.service`, user `wrendns` | the migration script moves both |
  | `TELLTALE_*` variables | `WRENDNS_*` | read when the new name isn't set, with a warning; the new name wins |
  | metrics `telltale_*` | `wrendns_*` | `/metrics` exports both |
  | headers `X-Telltale-Reason`, `X-Telltale-Client`; cookie `telltale_session` | `X-Wrendns-Reason`, `X-Wrendns-Client`; `wrendns_session` | both are read, so nobody is signed out; backup responses carry both header spellings |
  | Kubernetes label `telltaledns.io/group` | `wrendns.com/group` | read too while `[kubernetes] label` is the default |
  | `probe.telltale.invalid` | `probe.wrendns.invalid` | both are the node's own probe |
  | release files `telltale-<arch>-linux` | `wrendns-<arch>-linux` | none: only the new names are published |
  | image `ghcr.io/nbacheller/telltale` or upstream's `ghcr.io/paimonsoror/telltale` | `ghcr.io/nbacheller/wrendns` | none: pull the new name |
  | chart `ghcr.io/nbacheller/charts/telltale` | `oci://ghcr.io/nbacheller/charts/wrendns` | none: the old chart is no longer updated |

- **Native install: run `sudo sh install.sh` again.** The installer is `deploy/systemd/install.sh`; the README shows how to download it. It installs the new binary and runs `deploy/systemd/migrate-from-telltale.sh` (which you can also run alone, with `--dry-run` first). The script stops the old service, renames the user and group (same IDs), moves `/etc/telltale` and `/var/lib/telltale`, renames `telltale.toml` to `wrendns.toml` (keeping the original as `wrendns.toml.pre-wrendns`), carries your unit's edits and drop-ins over to `wrendns.service`, and leaves links at the old paths and at `/usr/local/bin/telltale`. If a step fails it starts the old service again. It lists other files that still name the old user, unit or command for you to change.
- **Don't use the old `telltale self-update` for this upgrade.** A TelltaleDNS build reads upstream's releases and trusts only upstream's key. Use `install.sh`. After the move, `sudo wrendns self-update --restart` works as usual; it reads this project's releases and installs only those signed with the WrenDNS key (key ID `4CBF504A8FBF5357`, `deploy/release/wrendns-release.pub`).
- **Docker Compose:** take the new `compose.yaml` and `wrendns.toml`, and stop the old project first (`docker compose down` in its directory) so two projects don't fight over port 53. Keep `./data`: it is mounted at `/var/lib/wrendns` and read as it is. A named volume needs one copy: `docker run --rm -v <old volume>:/from -v wrendns-data:/to busybox cp -a /from/. /to/`.
- **Helm:** a StatefulSet's selectors can't change, so upgrade a release named `telltale` with the old names pinned: `helm upgrade telltale oci://ghcr.io/nbacheller/charts/wrendns --version <version> --reuse-values --set nameOverride=telltale --set fullnameOverride=telltale`. Or install a new release named `wrendns` and restore a backup into it.
- **A cluster can be upgraded node by node,** replicas first and the primary last. Nodes of both versions talk to each other, and `deploy/cluster3/e2e.sh` checks that DNS answers on at least two nodes throughout. Before you start, check (read-only) that every node's registry lists every node (`wrendns cluster status` on the primary, or the Cluster page): a node missing from it comes back as an ephemeral member, with no key and no vote (`docs/security-review.md`).
- **Move your dashboards and alerts** from `telltale_*` to `wrendns_*` within this release. The bundled Grafana dashboard, service-level objective (SLO) rules and Helm alert rules already use `wrendns_*`. Scripts that send `X-Telltale-Reason` should send `X-Wrendns-Reason`.
- **Plugins** (`exec://` upstreams) get `WRENDNS_PLUGIN_SOCKET` and `WRENDNS_UPSTREAM`, and in this release also `TELLTALE_PLUGIN_SOCKET` and `TELLTALE_UPSTREAM`. They no longer inherit any other `WRENDNS_*` variable.
- **What stays as it was,** because it is in files you already have: backup files and their format name, the secrets key format (`ttsk1:`), the audit chain, and the API token prefixes (`tt_`, `tt_join_`). A backup made before the rename restores on this version.
- **Home Assistant integration 0.2.0 is a breaking change.** The domain `telltale` is now `wrendns`, and so are the event (`wrendns_anomaly`), the actions (`wrendns.*`) and the entity IDs. Nothing is migrated: install `custom_components/wrendns`, delete the old folder, add WrenDNS with the same token, delete the old entry, and rename what uses the old names. The old sensors' long-term statistics go with the old entry. See `integrations/home-assistant/CHANGELOG.md`.

### Credentials and secrets

These changes came after TelltaleDNS 0.7.x and apply to anyone coming from it. They first appeared in edge builds numbered 0.8.0, so the product's checks and messages name 0.8.0 as the first version that has them; 1.0.0 has them too. An edge build `0.8.0-edge.N` from before these changes also counts as 0.8.0: in a cluster that still runs one, upgrade the primary before making credential changes.

- **Credentials are no longer shown anywhere they were copied.** An upstream's `headers` and `args`, a password in any URL setting (an upstream's `url`, `proxy` or `relay`, an alert destination's or a list's `url`, `[cluster.git] repo`, and the others), an OIDC `client_secret`, and `[telemetry.otlp] headers` now read `<redacted>` in `GET /api/v1/config/entries`, write responses, the audit log, the TOML to keep a change in Git, agents' plans, pin and version diffs, MCP, and `wrendns config check --print` (`--show-secrets` prints them on the node). Sending back what you read keeps working: `<redacted>` keeps the stored value as long as the entry's `url`, `proxy`, `host`, `tls_server_name`, `tls_ca`, `bootstrap`, `tls_insecure_skip_verify`, `spki_pins` and (for an alert destination) `type` are unchanged. With a new destination it is refused (422 `credential_reentry_required`): send the credential itself.
- **Checks need credentials typed.** **Test it** (`POST /api/v1/checks/upstream`, `/checks/list`) on an existing upstream with headers, or a list whose URL has a password, no longer uses the stored value: the form holds `<redacted>`, which a check never resolves (422). Type the credential into the draft to test it.
- **During a rolling upgrade, make credential changes on the primary.** While the primary still runs 0.7, a change on an upgraded replica that sends `<redacted>` back (the UI and agents do, for an entry with a credential) is refused with 409 `upgrade_required`, since an older primary would store `<redacted>` as the value. Once the primary is upgraded, a change that touches a credential made on a 0.7 replica is refused the same way, since the replica can't say who made it.
- **Operators can no longer point a credential somewhere.** Changing an alert destination's `token_file` or `password_file` or an upstream's `tls_client_key`, moving an entry that holds a credential (its `url`, `proxy`, `host`, `tls_server_name`, `tls_ca` or `bootstrap`, an alert destination's `type`), weakening how it checks the other end (`tls_insecure_skip_verify`, `spki_pins`), and creating, changing or checking an `exec://` or `unix://` upstream now need the admin role. Operators get 403, and agent tokens always do, whatever their scopes (`config:write:alerts` and `config:write:upstreams` included). Other edits are unchanged.
- **Paths set through the UI or API are confined.** They may not be under `/proc`, `/sys`, `/dev`, the data directory or `/var/run/secrets/kubernetes.io`, or name a key file. A credential file must be in `[node] secret_file_dirs` (default `/run/secrets`, `/var/run/secrets`, `/etc/wrendns/secrets`, and in this release `/etc/telltale/secrets`). A list's `path` may not be in those directories, and a CA, client certificate or list may not name a credential file the node's configuration uses. A stored path that breaks this is **no longer read**: an alert destination or list fails as with a missing file; an upstream runs without it (the system's roots instead of a refused `tls_ca`, no client certificate if its certificate or key is refused, so an mTLS upstream is refused by its server). The log says why, and `GET /api/v1/config/entries` lists it under `credentialIssues`. Before upgrading, check your API-made alert destinations, lists and upstreams (an mTLS client key outside `secret_file_dirs`, or a CA in the data directory), and move their files or list the directory in `secret_file_dirs`. Paths in the configuration files are unaffected.
- **Older audit entries may hold credentials.** Entries written before this version recorded a change's full body, so an upstream's headers can be in them. The hash chain can't be rewritten: treat an older `state.db`, and backups made from it, as sensitive.
- **`Idempotency-Key` records start over.** The upgrade deletes the stored retry records (they held request bodies), so a retry of a request made before the upgrade is applied again rather than replayed. Records now keep a hash keyed with the node's new secrets key: `<data_dir>/secrets.key` (made on first start, mode 0600), `WRENDNS_SECRETS_KEY`, or `[node] secrets_key_file`.
- **The self-update** no longer passes on `WRENDNS_SECRETS_KEY`, `WRENDNS_SECRETS_PREVIOUS_KEY`, `WRENDNS_BOOTSTRAP_ADMIN_PASSWORD`, `WRENDNS_BOOTSTRAP_ADMIN_PASSWORD_HASH` or `WRENDNS_TOKEN`.
- **The Git webhook** answers a refused request with a plain 401 (the log says why), and an empty `webhook_secret_file` refuses every webhook.
- **Credentials can be stored secrets.** A credential read from a file (a router's keys and password, an alert destination's token and password, an OIDC client secret, a sink's token, OTLP headers, the Git source's credentials) can instead name a secret stored encrypted on the node (`api_key_ref = "unifi"`, `header_refs = { api-key = "otlp" }`). Setting two of a credential's inline value, `_file` and `_ref` is an error (the OIDC error now also names `client_secret_ref`), and so is `<redacted>` as a value in the configuration files: a file made from `config check --print` needs its credentials put back. Backups include stored secrets only when made with a passphrase (`--secrets-passphrase-file`, `--secrets-passphrase-stdin` or `--secrets-passphrase-prompt`, or in the API and the web UI), encrypted under it, and never the key (`docs/running.md`, "Stored secrets in a backup"). `wrendns secrets status` and `wrendns secrets rotate-key` are new (`docs/secrets.md`).
- **Stored secrets through the API.** `PUT`/`DELETE /api/v1/secrets/<name>` (admins only; agent tokens get `403 agent_not_allowed`) and `wrendns ctl secrets set|clear|list` set and clear them; `GET /api/v1/secrets` (operators, agents with `config:read`, the MCP tool `secrets_status`) lists them without values. Secret writes over plain HTTP from another host are refused (`403 insecure_transport`) unless `[api] allow_secrets_over_http = true`: put a TLS proxy in front or turn on `[api] tls`. In a cluster the primary keeps them and replicates them to full members. A replica forwards secret writes to the primary, so set secrets once the primary is upgraded (409 `upgrade_required` before). A write that adds a `*_ref` warns naming members still on 0.7, which keep their last configuration until upgraded.
- **A credential the configuration files set can't be changed through the API.** An override of a file-defined alert destination keeps the files' `token_file`/`password_file` when it leaves them out, and is refused (409 `set_by_file`) when it sets, replaces or removes one; hiding (`DELETE`) a file-defined destination that has one is refused too. Change the file instead.
- **Helm:** `secretsKey.existingSecret` mounts your own key for the stored secrets on the controller only (recommended). `secretsKey.generate` makes one with `lookup`, which doesn't work with `helm template` or Argo CD. With `persistence.enabled: false` the controller is told its data isn't kept (`WRENDNS_DATA_EPHEMERAL`), and health warns (`secrets_ephemeral`) while secrets are stored.

## Known issues

- **Syslog events are lost while a TCP or TLS collector is down,** and the sink's dropped count doesn't show them: it counts only events lost to a full queue. The log has one warning ("event sink can't reach its syslog collector") until a send works again.
- **A MAC-keyed client behind a router matches only on the node that polls the router.** A replica takes the router's leases from the primary for names, but not yet for its address-to-MAC map.
- **DNSCrypt** over an IPv6-only path without an IPv6 route isn't supported.
- **Two release gates are still open** (`docs/v1-gate.md`): cache-hit throughput on a Raspberry Pi 4 (at least 25k queries a second) hasn't been measured, and the p95 of a configuration reaching every node (at most 5 s) needs more published versions; single samples were under 5 s. Throughput was measured on a development host, not the reference hardware.
- **Fuzzing** covers the DNS wire format, upstream responses and the cache, the DoH HTTP/1.1 response reader, list parsing, the query-log segment reader, SNMP, the category catalog, the discovery worker frames, the inventory merge and the support package redactor (`fuzz/fuzz_targets/`). The cluster frame decoder, the backup and import archive readers and the cache dump loader have no fuzz target yet (`docs/security-review.md`).
- **Platforms:** Linux on x86-64, arm64 and 32-bit ARM (Raspberry Pi 3, 4, 5 and Zero 2 W), in a container and in Kubernetes. ARMv6 boards (Pi 1, Zero W) aren't supported. The Docker Desktop bundle for Windows and macOS is for trying WrenDNS only: it can't see real client addresses.
- **Not in this release:** WrenDNS serves no zones (zone transfers are answered `REFUSED`) and is not a public authoritative server. It can't import the results of a network scanner you run yourself.
