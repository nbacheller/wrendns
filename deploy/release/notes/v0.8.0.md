## Upgrading

- **Credentials are no longer shown anywhere they were copied.** An upstream's `headers` and `args`, a password in any URL setting (an upstream's `url`, `proxy` or `relay`, an alert destination's or a list's `url`, `[cluster.git] repo`, and the others), an OIDC `client_secret`, and `[telemetry.otlp] headers` now read `<redacted>` in `GET /api/v1/config/entries`, write responses, the audit log, the TOML to keep a change in Git, agents' plans, pin and version diffs, MCP, and `telltale config check --print` (`--show-secrets` prints them on the node). A tool that edits an entry by sending back what it read keeps working: `<redacted>` keeps the stored value as long as the entry's `url`, `proxy`, `tls_server_name`, `tls_ca`, and `bootstrap` are unchanged. A write that sends `<redacted>` with a new destination is refused (422 `credential_reentry_required`): send the credential itself.
- **Checks need credentials typed.** **Test it** (`POST /api/v1/checks/upstream`, `/checks/list`) on an existing upstream with headers, or a list whose URL has a password, used to send the stored value. The form now holds `<redacted>`, which a check never resolves (422): type the credential into the draft to test it.
- **Upgrade the primary first.** During a rolling upgrade, a change made on an upgraded replica that sends `<redacted>` back (the UI and agents do, for an entry with a credential) is refused with 409 `upgrade_required` while the primary still runs 0.7: an older primary would store `<redacted>` as the value.
- **Operators can no longer point a credential somewhere.** Changing an alert destination's `token_file` or `password_file` or an upstream's `tls_client_key`, moving an entry that holds a credential (its `url`, `proxy`, `tls_server_name`, `tls_ca` or `bootstrap`), and creating or changing an `exec://` or `unix://` upstream (and checking one) now need the admin role: operators get 403, and agent tokens always do, whatever their scopes (`config:write:alerts` and `config:write:upstreams` included). Other edits are unchanged.
- **Paths set through the UI or API are confined.** They may not be under `/proc`, `/sys`, `/dev` or the data directory, or name a key file, and a credential file must be in `[node] secret_file_dirs` (default `/run/secrets`, `/var/run/secrets`, `/etc/telltale/secrets`). A stored path that breaks this is **no longer read** (the alert, upstream or list fails as with a missing file, the log says why, and `GET /api/v1/config/entries` lists it under `credentialIssues`): check your API-made alert destinations before upgrading, and move their files or list the directory in `secret_file_dirs`. Paths in the configuration files are unaffected.
- **Upgrade the replicas too.** A change that touches a credential made on a 0.7 replica is refused by an upgraded primary (409 `upgrade_required`), since the replica can't say who made it; make such changes on the primary until the replicas are upgraded.
- **Older audit entries may hold credentials.** Entries written before this version recorded a change's full body, so an upstream's headers can be in them. The audit log's hash chain can't be rewritten: treat an older `state.db`, and backups made from it, as sensitive.
- **`Idempotency-Key` records start over.** The upgrade deletes the stored retry records (they held request bodies); a retry of a request made before the upgrade is applied again rather than replayed. Records now keep a hash keyed with the node's new secrets key, `<data_dir>/secrets.key` (made on first start, mode 0600), or `TELLTALE_SECRETS_KEY` / `[node] secrets_key_file`.
- **Plugins** no longer inherit any `TELLTALE_*` variable except `TELLTALE_PLUGIN_SOCKET` and `TELLTALE_UPSTREAM`. **The self-update** no longer passes on `TELLTALE_SECRETS_KEY`, `TELLTALE_SECRETS_PREVIOUS_KEY`, `TELLTALE_BOOTSTRAP_ADMIN_PASSWORD`, `TELLTALE_BOOTSTRAP_ADMIN_PASSWORD_HASH`, or `TELLTALE_TOKEN`.
- **The Git webhook** answers a refused request with a plain 401 (the log says why), and an empty `webhook_secret_file` refuses every webhook.
