## Upgrading

- **Credentials are no longer shown anywhere they were copied.** An upstream's `headers` and `args`, a password in any URL setting (an upstream's `url`, `proxy` or `relay`, an alert destination's or a list's `url`, `[cluster.git] repo`, and the others), an OIDC `client_secret`, and `[telemetry.otlp] headers` now read `<redacted>` in `GET /api/v1/config/entries`, write responses, the audit log, the TOML to keep a change in Git, agents' plans, pin and version diffs, MCP, and `telltale config check --print` (`--show-secrets` prints them on the node). A tool that edits an entry by sending back what it read keeps working: `<redacted>` keeps the stored value as long as the entry's `url`, `proxy`, `host`, `tls_server_name`, `tls_ca`, `bootstrap`, `tls_insecure_skip_verify`, `spki_pins` and (for an alert destination) `type` are unchanged. A write that sends `<redacted>` with a new destination is refused (422 `credential_reentry_required`): send the credential itself.
- **Checks need credentials typed.** **Test it** (`POST /api/v1/checks/upstream`, `/checks/list`) on an existing upstream with headers, or a list whose URL has a password, used to send the stored value. The form now holds `<redacted>`, which a check never resolves (422): type the credential into the draft to test it.
- **Upgrade the primary first.** During a rolling upgrade, a change made on an upgraded replica that sends `<redacted>` back (the UI and agents do, for an entry with a credential) is refused with 409 `upgrade_required` while the primary still runs 0.7: an older primary would store `<redacted>` as the value.
- **Operators can no longer point a credential somewhere.** Changing an alert destination's `token_file` or `password_file` or an upstream's `tls_client_key`, moving an entry that holds a credential (its `url`, `proxy`, `host`, `tls_server_name`, `tls_ca` or `bootstrap`, an alert destination's `type`) or weakening how it checks the other end (`tls_insecure_skip_verify`, `spki_pins`), and creating or changing an `exec://` or `unix://` upstream (and checking one) now need the admin role: operators get 403, and agent tokens always do, whatever their scopes (`config:write:alerts` and `config:write:upstreams` included). Other edits are unchanged.
- **Paths set through the UI or API are confined.** They may not be under `/proc`, `/sys`, `/dev`, the data directory or `/var/run/secrets/kubernetes.io`, or name a key file; a credential file must be in `[node] secret_file_dirs` (default `/run/secrets`, `/var/run/secrets`, `/etc/telltale/secrets`); a list's `path` may not be in those directories, and a CA, client certificate or list may not name a credential file the node's configuration uses. A stored path that breaks this is **no longer read** (an alert destination or list fails as with a missing file; an upstream runs without it: the system's roots instead of a refused `tls_ca`, no client certificate if its certificate or key is refused, so an mTLS upstream is refused by its server; the log says why, and `GET /api/v1/config/entries` lists it under `credentialIssues`): check your API-made alert destinations, lists and upstreams (an mTLS client key outside `secret_file_dirs`, such as `/etc/telltale/client.key`, or a CA in the data directory) before upgrading, and move their files or list the directory in `secret_file_dirs`. Paths in the configuration files are unaffected.
- **Upgrade the replicas too.** A change that touches a credential made on a 0.7 replica is refused by an upgraded primary (409 `upgrade_required`), since the replica can't say who made it; make such changes on the primary until the replicas are upgraded.
- **Older audit entries may hold credentials.** Entries written before this version recorded a change's full body, so an upstream's headers can be in them. The audit log's hash chain can't be rewritten: treat an older `state.db`, and backups made from it, as sensitive.
- **`Idempotency-Key` records start over.** The upgrade deletes the stored retry records (they held request bodies); a retry of a request made before the upgrade is applied again rather than replayed. Records now keep a hash keyed with the node's new secrets key, `<data_dir>/secrets.key` (made on first start, mode 0600), or `TELLTALE_SECRETS_KEY` / `[node] secrets_key_file`.
- **Plugins** no longer inherit any `TELLTALE_*` variable except `TELLTALE_PLUGIN_SOCKET` and `TELLTALE_UPSTREAM`. **The self-update** no longer passes on `TELLTALE_SECRETS_KEY`, `TELLTALE_SECRETS_PREVIOUS_KEY`, `TELLTALE_BOOTSTRAP_ADMIN_PASSWORD`, `TELLTALE_BOOTSTRAP_ADMIN_PASSWORD_HASH`, or `TELLTALE_TOKEN`.
- **The Git webhook** answers a refused request with a plain 401 (the log says why), and an empty `webhook_secret_file` refuses every webhook.
- **Credentials can be stored secrets.** Each credential read from a file (a router's keys and password, an alert destination's token and password, an OIDC client secret, a sink's token, OTLP headers, the Git source's credentials) can instead name a secret stored encrypted on the node (`api_key_ref = "unifi"`, `header_refs = { api-key = "otlp" }`). Setting two of a credential's inline value, `_file` and `_ref` is now an error (an OIDC provider with both `client_secret` and `client_secret_file` already was; the error now names `client_secret_ref`), and so is `<redacted>` as a value in the configuration files (it's what a redacted copy shows: a file made from `config check --print` must have the credentials put back). Backups never include stored secrets or the key. `telltale secrets status` and `telltale secrets rotate-key` are new.
- **A credential the configuration files set can't be changed through the API.** An override of a file-defined alert destination keeps the files' `token_file`/`password_file` when it leaves them out, and is refused (409 `set_by_file`) when it sets, replaces or removes one; hiding (`DELETE`) a file-defined destination that has one is refused too. Change the file instead.
- **Helm:** `secretsKey.existingSecret` mounts your own key for the stored secrets on the controller only (recommended); `secretsKey.generate` makes one with `lookup` (not for `helm template` or Argo CD). With `persistence.enabled: false` the controller is told its data isn't kept (`TELLTALE_DATA_EPHEMERAL`), and health warns while secrets are stored.
